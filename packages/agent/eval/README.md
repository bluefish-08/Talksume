# 对话 Agent 评测

三套评测，都直连官方 DeepSeek（默认 `deepseek-flash`，不开思考），key 从主仓库的 `.env` 读，不打印。

| 评测                    | 目录                       | 测什么                                                                                        | 一次全量                  |
| ----------------------- | -------------------------- | --------------------------------------------------------------------------------------------- | ------------------------- |
| 防编造 eval             | `run.ts` + `samples.jsonl` | 台词写死、主动全说，测抽取的 P/R                                                              | 6 段                      |
| 第 1 层：冻结状态探针   | `probes/`                  | 重建某个时刻的完整状态，对下一句用户话重放 N 次，看这一轮写没写对、跳没跳、问了几句、收没收尾 | 12 个探针 × 8 次 ≈ 2 分钟 |
| 第 2 层：多人设整段对话 | `personas/`                | 模拟用户按人设聊完一整段，看召回、准确性、空/重复条目、问句、收尾、假称、耗时                 | 5 人设 × 8 次 ≈ 15 分钟   |

S0 之后每一步改动是否合并，以第 1、2 层的结果和下面的门槛为准。

## 怎么跑

都在 `packages/agent` 下执行。`--target` / `--a` / `--b` 可以是另一个 checkout 的目录，也可以是 git ref（自动检出到临时 worktree 并离线安装依赖）。

```bash
node eval/probes/run.ts --n 8 --out eval-out/probes-base
```

```bash
node eval/probes/run.ts --n 8 --replay intake --out eval-out/probes-replay
```

```bash
node eval/probes/run.ts --show
```

```bash
node eval/personas/run.ts --reps 8 --out eval-out/personas-base
```

```bash
node eval/personas/run.ts --a main --b ../my-worktree --reps 8 --out eval-out/ab
```

```bash
node eval/gate.ts --base eval-out/probes-base.json --cand eval-out/probes-new.json --personas eval-out/ab.json
```

```bash
node eval/personas/calibrate.ts
```

- `probes/run.ts`：`--only id1,id2` 只跑部分探针；`--replay main|intake` 切换历史形态（`main`：`meta.tools` 只有岗位工具，S1a 之前的线上形态；`intake`：建档工具调用也写进历史回放，记录经被测代码的 `replayRecord` 处理，和线上一致）。不给时按被测代码定：导出了 `replayRecord` 就用 `intake`，否则 `main`；`--show` 不调模型，只打印每个探针重建出的状态（每轮的 slot、工具报错、规划器下一个目标），改台词后先看一眼。
- `personas/run.ts`：给了 `--b` 就两个版本交替跑（同一人设同一轮次 A、B 相邻，奇偶轮次换先后），抵消上游随时间的漂移；`--personas thin,intern` 只跑部分人设；`--no-judge` 不跑假称判定；`--from x.runs.jsonl` 不调模型，只从已存的运行记录重算报告，加 `--rejudge` 则用当前判定器重新判定假称（改了判定器后用）。每跑完一次就追加到 `.runs.jsonl`，中途断了也不丢。
- 输出：`<out>.json`（完整数据）和 `<out>.md`（汇总表）。`eval-out/` 已加进 `.gitignore`。

## 第 1 层：探针

- 状态由 `probes/builder.ts` 从「台词 + 每轮写入的事实」重建：事实经**真实的** `upsert_facts`（quote 校验、暂存、冲突检测、`liftSkips` 都照常）写入，`meta.slot` 取当时规划器的目标（可用正则指定），`askCounts` 按 `noteAsked` 累计。台词本身写不进去时 `--show` 会显示「!」。
- 判定全在 `probes/checks.ts`，比较本轮前后的状态：画像各分区条目数、新写入的事实、新增跳过、待确认矛盾、回复里的问句数、收尾、是否调用了岗位工具。
- 检查分两类，分开统计：**写入类**（条目数、写入、跳过、矛盾、岗位调用）合起来是「写入正确率」，合并门槛只看它；**回复类**（问句数、收尾，表里标〔回〕）合起来是「回复合规率」，S3 用。混在一起会把几乎每个探针都拉到中间概率，重复跑波动变大。每条检查另有「计入通过」和「只观察」（表里带 *）之分。
- 某些探针要复现审查实验的状态（`skills-answer`、`no-info`、`confirm-then-name`），台词设了 `countAsks: false`，不累计 `askCounts`，规划器目标停在空条目「Java 课程设计」的担任角色上。
- 问句数：以问号结尾的句子；紧跟在问句后、以「比如 / 或者 / 还是 / 你是怎么解决的」开头的补充问不另算。快捷回答行不算。
- 收尾：用评测侧固定的一份 `WRAP` 正则（抄自 `tools.ts`），被测代码改了正则也不影响判定。
- 一次试验如果模型调用出错（上游超时等），整次重来，最多 3 次；还出错就记为失败并在表里单列「基础设施失败」。

## 第 2 层：多人设

- 人设在 `personas/personas.ts`：经历少的专科生（李明）、有实习的本科生、转专业的、一次说很多的、爱跑题的，全是虚构信息。每个人设带一份标准答案画像，格式同 `samples.jsonl` 的 `$contains`。
- 模拟用户、假称判定器固定用当前 checkout 的网关和 `deepseek-flash`，A/B 两边一致。被测 agent 的备用模型钉成同一个模型，避免重试耗尽时换成 pro 混进结果。
- 对话在第一次收尾（第 6 轮之后）后再让用户回一句，用来看「收尾后又追问」，然后结束；最多 30 轮。

| 指标               | 定义                                                                                                                                           |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 召回               | 标准答案里每一项，用户原话里出现过（日期、学历、类别按常见说法匹配，其余按归一化包含或字对覆盖率 ≥0.75）才进分母；分子是其中被记下的           |
| 准确性 P           | 沿用 `metrics.ts` 的 `scoreProfile`：tp / (tp + fp)，没对上标准答案、但照原话写的要点不算误报                                                  |
| 准确性 P（按原话） | 同上，但误报只算用户原话里找不到的写入。模拟用户偶尔会多说设定外的内容（如课程名），agent 照实记下不该算编造；门槛 3a 看这一行，上一行只作参考 |
| 无依据写入         | 每次运行里「按原话」口径的误报条数，报告 JSON 的 `perRun[].unfounded` 列出具体内容                                                             |
| 空条目             | 实习 / 项目条目除了名字和类别什么都没有                                                                                                        |
| 疑似重复条目       | 名字互相包含或字对覆盖率 ≥0.5，或两个条目引用了同一句原话                                                                                      |
| 问句 >1            | 一条回复里问句数大于 1 的轮次占比，问句数规则同探针                                                                                            |
| 收尾后又提问       | 第一次收尾的回复里收尾句后面还有问号，或者下一轮回复又问了问题                                                                                 |
| 过早收尾           | 第一次收尾时，规划器的下一个目标仍是必填项                                                                                                     |
| 假称已记录         | flash 当判定器，逐轮看回复是否声称记录了某内容，再对照本轮实际写入和之前的画像；见下                                                           |
| 耗时、token        | 首字和整轮耗时的 p50/p90；每轮模型调用次数、输入 token（含缓存命中）、输出 token                                                               |

比率按「先合并再除」计算；置信区间是按运行聚类、按人设分层的 bootstrap（2000 次，固定种子）。两版本时另给「后 − 前」的差和区间。

### 假称判定器

`personas/judge.ts`，temperature 0。上线前用 `personas/claim-samples.jsonl` 的 40 条样本校准：30 条取自审查实验的冒烟记录和定点实验，10 条是 S0 基线里的难例（复述、「这块不写了」、承诺式说法），人工标注，含 16 条假称。改了判定器提示词就重跑 `calibrate.ts`，准确率低于 90% 不要用。

## 合并门槛

动工前写死（审查报告第 3 节）。`eval/gate.ts` 自动判定：

1. 探针集的总通过率提升，且 95% 置信区间不跨 0（按探针分层的 bootstrap）；
2. 任何单个探针不退步超过 2/8；
3. 防编造（多人设 A/B，改抽取时另跑 `run.ts` 的防编造 eval 一并看），分两条：
   - 3a 按原话口径的 P（用户说过的内容不算误报）不显著下降，即差的 95% 区间上界 ≥ 0；
   - 3b 编造 (c) 每次运行的均值不高于基线。需要审计输出（`--audit`）；没有审计输出时判「缺数据」，不能算通过；
4. 整段对话里的空或重复条目为 0（新版本，所有人设所有运行）；
5. 首字 p50 不比基线慢 20% 以上（多人设 A/B，同时段交替运行）。

门槛 3 改过（2026-11-05 用户决定）。原来是「沿用 eval 的 P 下降不超过 1 个百分点」，这个口径把用户答了、但不在人设预期画像里的内容（主修课程、技术栈、自我介绍等）也算成误报，S1c 实测约占新增误报的 4/5，会把「问得更全」当成准确性下降。新口径只把添加了用户没说过的事实算作问题；把用户说过的内容改写成简历措辞（「一个人做的」→「独立完成」、「熟悉」→ familiar）不算。沿用 eval 的 P 仍在报告里列出，作为参考，不进门槛。

各阶段还有自己的验收（`docs/Agent设计诊断.md` 第 6 节），例如 S1a 要求技能探针 ≥7/8、S1b 要求「确认后说出名字」探针 8/8 只有一个条目。

### 编造审计（门槛 3b）

`personas/audit.ts` 把多人设运行里每个 fp 单元分成三类：

- (a) 原话里说过：用评测自带的 `saidIn` 判；
- (b) 由原话改写或直接推断；
- (c) 添加了原话里没有的事实、数字、名称、程度或职责。

(b)/(c) 的拆分由 temperature 0 的 LLM 完成。它只是分类器，不是评委，没有像假称判定器那样用标注样本校准。已知误差：S1c 里手工抽查了 14 条覆盖最低的 highlights，2 条有轻微补充（「退货量大」「接口随之通畅」）被分类器归在 (b)；同一批数据重跑，(c) 的计数会有 ±1～2 的波动。分类器连续三次失败的单元按 (c) 计，宁可多报，不让失败放过门槛。

```bash
node eval/personas/audit.ts --from eval-out/ab.runs.jsonl --out eval-out/ab.audit
```

```bash
node eval/gate.ts --base eval-out/probes-base.json --cand eval-out/probes-new.json --personas eval-out/ab.json --audit eval-out/ab.audit.json
```

`--from` 的运行记录要只含这一次 A/B（`run.ts` 追加写 `.runs.jsonl`，同一个 `--out` 重跑会混进旧记录）。

## 已知局限

- 探针 N=8 时，单个探针在 50% 左右的通过率上两次重复跑相差 2/8 并不罕见（二项分布本身的波动）。要分辨 4/8 对 0/8 这种幅度，把那个探针的 N 提到 16。
- 召回的「说过」靠关键词匹配，用户换了说法（「成绩系统」对「学生成绩管理系统」）会被排除出分母，偏乐观。
- 多人设对话的路径受模拟用户影响很大，单个人设 8 次只能看出大的差别；中等改进以探针为准。
- 并发跑会让上游首字变慢，耗时只在同一次 A/B 交替运行里比较，不要跨批次比。
